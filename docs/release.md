# Release

How a BitGauge release is versioned, built and published, what to do when a release fails halfway,
and what has to be set up by hand for all of it to hold. The pipeline is
[`.github/workflows/release.yaml`](../.github/workflows/release.yaml), built from the shared
actions of [gh-composite-actions](https://github.com/leinardi/gh-composite-actions)
(`release-version`, `require-ci-green`, `require-job-success`, `release-mode`,
`toolchain-record`, `toolchain-recover`, `check-pinned-bases`, `trivy-gate`,
`binary-attestation-status`); this page, with
[build-packaging.md §4](features/technical-stack/build-packaging.md#4-ci-workflows), is why it is
shaped that way.

**There has been no release yet.** Before the first dispatch, dry runs included, do the
[one-time setup](#one-time-setup).

## What a Release Produces

- Two static musl binaries, `bitgauge-linux-amd64` and `bitgauge-linux-arm64`, built by
  `make rust-release-binaries` with the pinned zig and cargo-zigbuild and the build paths remapped,
  with the version, commit and commit date compiled in through the `BITGAUGE_*` stamps and the SPA
  embedded. The SPA is built once, by the same make target, and both binaries embed that one
  build. A `checksums.txt` file covers both. All three files are attached to the GitHub release,
  and each binary has a build provenance attestation made by the release workflow
  ([attestations](https://docs.github.com/actions/security-guides/using-artifact-attestations)).
- One multi-arch (`linux/amd64`, `linux/arm64`) image, `ghcr.io/leinardi/bitgauge:X.Y.Z`, built
  from the Dockerfile's `prebuilt` target: **each platform's image binary is that platform's
  release binary, byte for byte**, SPA included. It carries an SPDX SBOM and a `mode=max` SLSA
  provenance attestation for every platform image, a build provenance attestation, and a keyless
  [cosign](https://docs.sigstore.dev/) signature on the image digest, made with the release
  workflow's own GitHub OIDC identity; no signing key exists anywhere. Before the version was
  tagged, CI had passed on the commit ([What CI Proves](#what-ci-proves)), and both platform images
  passed the release's smoke test and a [Trivy](https://trivy.dev/) scan with no fixable `HIGH` or
  `CRITICAL` vulnerability outside [`.trivyignore.yaml`](../.trivyignore.yaml).
- The moving image tags `X` and `latest` of [Tags](#tags), and the GitHub "Latest" release marker,
  when the version is the highest released one.
- Release notes that name the Rust and Node versions the binaries were built with and the base
  digest each platform image was built on (read from the build's provenance), followed by notes
  generated by GitHub from the merged pull requests.

[SECURITY.md](../SECURITY.md#verifying-a-release) shows how to verify an image or a binary.

## How to Release

1. Make sure `main` is green, the accuracy harness's CI tier passes when dispatched by hand
   (`harness.yaml`), and its manual floor and ceiling tiers and the real Safari and iOS checks have
   passed for this commit and are recorded in
   [`engineering/harness-runs/<version>.md`](engineering/harness-runs/README.md), the first being
   `0.1.0.md`. A release is blocked until they have ([features/technical-stack/testing.md
   §6](features/technical-stack/testing.md#6-ci-placement)). v0.1.0 was the one exception: it
   shipped on the CI tier alone, by the maintainer's decision, and
   [its file](engineering/harness-runs/0.1.0.md) says what was not run.
2. Run the **Release** workflow (`release.yaml`) from the Actions tab, or
   `gh workflow run release.yaml`, on `main`, once CI has run on the commit's push to `main`: the
   `ci-green` job waits for that run for up to 30 minutes, and fails if it did not pass. The
   workflow is `workflow_dispatch` only and takes two inputs:
   - `version`: optional, `X.Y.Z` or `vX.Y.Z`. Left empty, the version is derived from the
     commits since the last release (see [Versioning](#versioning)). The first release needs it,
     since there is no tag to derive from. Give it explicitly to force a version, or to recover a
     failed run with a fresh dispatch (see
     [Recovering a Failed Release](#recovering-a-failed-release)).
   - `dry_run`: boolean, default `false`. See [Dry Runs](#dry-runs).

Nobody creates or pushes a tag by hand: the workflow builds, tests, scans and verifies everything
first, and pushes the tag itself only then (see
[Why the Build Happens Before the Tag](#why-the-build-happens-before-the-tag)).

**One release runs at a time.** `release.yaml` takes the `release` concurrency group with
`cancel-in-progress: false`, so a second dispatch queues behind the first instead of racing it. Two
runs in flight together would each check their version against the same latest tag, both pass, and
then publish in whatever order they finished, and a lower version landing last would take `latest`
with it. A run that has started is never cancelled part-way through publishing.

## Versioning

Semantic versioning, derived from
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) by
[`svu`](https://github.com/caarlos0/svu), through gh-composite-actions' `release-version`:

- `feat` is a minor.
- `fix` is a patch.
- `!` before the colon, or a `BREAKING CHANGE:` footer, is a major. Before `1.0.0`, `svu` turns a
  breaking change into `1.0.0` straight away; while BitGauge is on `0.x`, release a breaking change
  with an explicit version if it should stay on `0.x`.

Everything else (`build`, `chore`, `ci`, `docs`, `perf`, `refactor`, `revert`, `style`, `test`)
bumps nothing, and the highest bump among the commits wins. A change users should receive in the
binary, the image or the web app is committed as `fix` or `feat`, even when it is a performance
improvement, a refactor or a revert; `perf`, `refactor`, `style` and `revert` are for changes
deliberately not meant to trigger a release, and a revert of a shipped `feat` or `fix` is itself a
`fix`. `svu` matches `feat`/`fix` anywhere in the subject, so `prefix:` counts as `fix:`. Pull
requests land as merge commits, so every commit counts, not only the pull request title
([AGENTS.md](../AGENTS.md#commit-messages)). When no commit since the last release is a `feat`, a
`fix` or a breaking change, a run with no version **fails** and asks for an explicit version. The
one exception is a recovery: when the derived version is a strict tag that already sits on `HEAD`,
the run treats it as a recovery of that version, so re-running a failed run that derived its
version works. `svu` is installed only to derive a version: a version typed by hand releases even
while GitHub's release downloads fail.

Dependabot's Cargo dependency, runtime npm and `docker` base-image updates are committed as
`fix(deps)`, so any of them alone is enough for a patch release. Its `github-actions` and
`pre-commit` updates, and Cargo dev-dependency and npm devDependency updates, stay `chore(deps)`
and bump nothing. A base-image security fix that `dhi.io` republished under the tag the Dockerfile
names makes no commit at all; the next release build picks it up, so it ships with an explicit
version when there is nothing else to release, and the [scheduled scan](#scheduled-scan) is what
says one is needed.

Only strict `vMAJOR.MINOR.PATCH` git tags are releases: `v`, then three dot-separated numbers, each
`0` or a number with no leading zero, and nothing after them, which is
`^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` (`RELEASE_TAG_REGEX` in the workflow, the
same regex `release-version` and `release-mode` use). An explicit version must match too, so
`01.2.3`, `1.02.3`, `1.2.3-rc.1`, `1.2.3+meta`, `1.2` and `v1.2.3.4` are refused. Every lookup
filters the full tag list through that regex, never a glob, so pointer tags such as `latest` or
`v1`, pre-release, build-metadata and malformed tags can never become the current version or stop
the version from resolving. `svu` is given the exact tag to count from: the highest strict tag
reachable from `HEAD`.

A new version must be higher than every version already released. **A pushed tag is never moved,
deleted or reused**: an immutable-tags ruleset forbids it, and the workflow never needs it, because
the tag is pushed only after everything that can fail without a tag has succeeded. The only
version a run may reuse is the one it is recovering, which is exactly that tag already sitting on
`HEAD`. A branch whose history does not contain the highest release derives from an older base and
fails that check; the failure names the out-of-history tag, and an explicit version higher than it
is the way out.

### Stray Local Tags

CI fetches only the tags on `origin`, so it is unaffected by anything in a local clone. A local
`svu next` is not: a strict tag that exists only locally is read like any other. Remove tags that
are not on `origin` before reasoning about versions locally:

```bash
git fetch --prune --prune-tags origin   # drops local tags that origin does not have
```

## Why the Build Happens Before the Tag

The `v*` tags are protected by an immutable-tags ruleset (no update, no deletion, no bypass), so a
"delete the tag on failure" cleanup cannot exist: it would fail every time, and a failed release
would leave a tag nobody can remove. Everything that can fail without a tag happens before the tag
exists, and everything after it can be finished by a re-run on the tagged commit (see
[Recovering a Failed Release](#recovering-a-failed-release)).

The run has four jobs:

1. **`guard`**: refuse anything but `main`, failing rather than skipping when `github.ref` is not
   `refs/heads/main` (`workflow_dispatch` lets the caller pick any branch, and the release job holds
   `contents: write`, `packages: write` and an OIDC identity); then resolve the version, as in
   [Versioning](#versioning), and read the stamps from the commit.
2. **`ci-green`**, after `guard`: `require-ci-green` on the commit. CI's run for the push of this
   exact commit to `main` (`.github/workflows/ci.yaml`, by file path, not by a check name any
   workflow could reuse) must have concluded with its `ci-result` job passing on the run's newest
   attempt. This replaces the release-time Rust and web checks and the full image tests
   ([What CI Proves](#what-ci-proves)).
3. **`audit`**, alongside the two: `make audit-deps`, cargo deny over the workspace's graph
   (advisories, licences, bans and sources) and `npm audit` of `web/`, the one time-sensitive check
   of the code, since advisories are published every day. It needs nothing and nothing needs it, so
   it runs while the release job builds and costs the release almost no time: the release job waits
   for it (`require-job-success`) only right before its first step that publishes anything, dry
   runs included, and stops unless it passed.
4. **`release`**, in the `release` environment, with `contents: write`, `packages: write`,
   `id-token: write`, `attestations: write` and `actions: read`. It checks the Dockerfile pins
   (`check-pinned-bases`, as CI does), sets up the pinned Rust and the newest patch of the Node
   major (on a recovery, the exact versions the tag records, through `toolchain-recover`), and then
   **decides the mode** (`release-mode`) from the git tag on the remote, the image
   `ghcr.io/leinardi/bitgauge:X.Y.Z`, the GitHub release and its assets. Only "not found" counts as
   absent: any other lookup error stops the run, because reading it as "absent" could push a tag or
   an image over something the run could not see.

   | Git tag | Published | Mode |
   | --- | --- | --- |
   | absent | nothing | **Fresh** |
   | absent | the image `:X.Y.Z`, or a GitHub release | **Stop before tagging**: the version is held |
   | on another commit |  | **Stop**: tags are immutable, release a higher version |
   | on this commit | the image, attested and cosign-signed by this workflow for this commit | **Recovery, reuse** |
   | on this commit | no image | **Recovery, publish** |
   | on this commit | anything unattested, unsigned, or differing from the image | **Stop: needs a human** |

   A tag on this commit must be annotated, in the clone, and record the toolchains this run builds
   with (`Rust: 1.N.N`, `Node: v24.N.N`), as this workflow writes them. The tag is then created
   **locally only**, if it does not exist yet. The private repository's tags are read from the
   remote with the token passed to those git commands only; the checkout keeps no credentials.

A **fresh** release then runs:

1. **Build once**: `make rust-release-binaries`, the make target CI builds with, builds the SPA
   once, then the two static binaries that embed it, with zig and cargo-zigbuild from
   gh-composite-actions' `setup-zigbuild` at the versions `.mk/rust-release.mk` pins; then
   `make rust-release-checksums` writes `checksums.txt`. The Rust build cache is the release's own
   (`prefix-key: release`), written only by this workflow.
2. Start a registry inside the job (`registry:3.1.2`, pinned by digest).
3. **Build the image once**, the Dockerfile's `prebuilt` target, for both platforms, with those
   binaries as the `dist` build context, so the image binary is the release asset. It is pushed by
   digest to the job-local registry, with the SBOM and `mode=max` provenance, every layer
   recompressed as gzip: the `dhi.io` base layers are zstd, and for a zstd image skopeo rewrites the
   index entries with a compression annotation, which the digest-preserving copy of step 9 then
   refuses. There is no layer cache: the target is the base plus one COPY.
4. **Record the base the build used**: the base is pinned by tag, so each platform's provenance
   names the digest the tag resolved to. The build must have pulled exactly one digest of the base
   tag and the `# syntax=` frontend pin, and nothing else (apart from BuildKit's SBOM scanner,
   which generates the SBOM and is not part of the image); the digests go into the release notes
   and the summary, as the exact base the release shipped.
5. **Smoke-test and scan both platform images**, each pulled back from the job-local registry by
   its own digest: `scripts/image-test.sh --tier smoke` checks that the image binary's SHA-256 is
   the release asset's, and that the container logs the release's version and commit in its
   startup line, reports the version, commit and build date on `/api/v1/info`, passes its
   `healthcheck` subcommand and serves the SPA's index page and every script and stylesheet it
   links (arm64 under QEMU). The binary has no `--version`; a build argument that did not reach it
   fails here, before the tag. Then `trivy-gate` scans each one (see
   [The Scan Gate](#the-scan-gate)).
6. **Gate the tag.** The highest released version is read again, from the remote, because a tag can
   arrive from outside the workflow while it builds; a fresh release that is no longer the highest
   fails with nothing pushed.
7. **Check the version image is absent**, right before the tag, with the same fail-closed lookup:
   the tag must never point at a version an image already holds. Then the release job waits for the
   `audit` job of its own run attempt to pass.
8. **Push the tag**: the point of no return. The token reaches this one git command as an HTTP
   header.
9. **Copy to GHCR, untagged**: `skopeo copy --all --preserve-digests` from the job-local registry to
   `ghcr.io/leinardi/bitgauge@<digest>`, with skopeo run from an image pinned by digest. The index
   keeps its digest, and its SBOM and provenance manifests come along.
10. **Check, attest, sign.** The index GHCR serves under the digest is hashed and must equal the
    tested digest; then the digest is attested and signed (`cosign sign --yes`).
11. **Tag the image** `X.Y.Z`, after checking once more that the tag is absent: a version tag that
    appeared since is never overwritten.

The binary attestations, the release assets and the latest pointers follow, in every mode, as
described under [Recovery Guarantees](#recovery-guarantees).

Everything stamped into an artifact comes from the commit rather than from the clock: the version,
a fixed seven-character commit prefix, the commit date as the build date (and the image's `created`
label), and the commit time as BuildKit's `SOURCE_DATE_EPOCH`. The binaries are built with the
exact toolchains recorded in the tag, `Cargo.lock` and `web/package-lock.json`, and
`--remap-path-prefix` for the checkout, the cargo home and the toolchain's sources, so a re-run of
the same commit produces the same bytes, which is what lets a recovery check published assets by
SHA-256. The image is not byte-reproducible: its provenance records the build itself, so two builds
of the same commit have different index digests. That is why a recovery never compares a rebuilt
index with a published one, and never rebuilds a published one.

## What CI Proves

The release runs no clippy, no test suite, no web check and only a short smoke test of the image.
That is sound only because CI already ran them on the same inputs, and the `ci-green` job pins that
to the commit being released:

- **The same commit.** `require-ci-green` accepts only the `push` run of `ci.yaml` whose head is the
  release's own SHA, on `main`, and its `ci-result` job must have passed on the run's newest
  attempt.
- **The code was tested on that commit.** `ci-result` needs `rust` (rustfmt, clippy, the tests, the
  docs, cargo-deny and the shipped graph's bans), `web` (the API type drift check, ESLint, vue-tsc,
  vitest, the build, the dist URL allowlist and the engine chunk size), `repo-gates` (the
  meta-tests), `pre-commit-all` (every hook on every file), `audit` and `e2e` (Playwright on
  Chromium, Firefox and WebKit).
- **The packaging was tested on that commit.** `ci-result` needs the `image` job, which runs on
  every pull request and every push, with no path filter. It builds the SPA and the static binaries
  with `make rust-release-binaries`, the release's own make target, then the `prebuilt` image
  target from them for both platforms:
  - **linux/amd64, the full tier** (`make image-test IMAGE_TEST_TIER=full`):
    `scripts/image-test.sh --tier full` checks that the image is the platform's; its binary is the
    `dist/` binary just built, byte for byte; the container logs the stamps in its startup line and
    reports them on `/api/v1/info`, passes its `healthcheck` subcommand and serves the SPA's index
    page and every script and stylesheet it links; the binary is a static x86-64 ELF,
    `0755 root:root`; the image runs as `65532:65532`, with the binary as its entrypoint, port 8080
    exposed, the binary's own `healthcheck` as its health check, no volume and the stamps as its
    labels; and the container, hardened (read-only root, no-new-privileges, every capability
    dropped), becomes healthy, stops cleanly on SIGTERM, and fails to start with exit status 2 on an
    invalid configuration. Then the image and netguard suites (testenv, feature `image`,
    [testing.md §5](features/technical-stack/testing.md)) run on the same image: no packet out, no
    write, and under strace no connection or write attempt.
  - **linux/arm64, the reduced tier** under QEMU (`--tier reduced`): the same up to the image
    config: the ELF machine and static linking, the mode and owner, the image config, the container
    starting, its stamps, its health check subcommand and the SPA it embeds.
- **The same build.** CI and the release build the binaries with the same make target, toolchain,
  zig and cargo-zigbuild (one value each, `meta/tests/toolchain.rs`), and the image from the same
  Dockerfile target and build context shape. The build arguments differ only in the stamps.
- **The same base tag, not always the same base digest.** The `dhi.io` bases are pinned by tag,
  deliberately not by digest: `dhi.io` rebuilds its tags too often for digest pins to be worth
  following by hand. `check-pinned-bases` (with `tag-only-images: dhi.io`) fails CI and the release
  on a `dhi.io` base with no explicit tag or on `latest`, on any other image without a digest, and
  on any download not followed by a checksum check. So the release may build on a newer rebuild of
  `dhi.io/static:<tag>` than the one CI tested. That is the accepted trade-off of pinning by tag: a
  rebuild of a distroless static base carries no code of ours, and what covers the base the release
  ships is the release's own smoke test and `trivy-gate` scan of that exact image, both before the
  tag. The release notes record the digest it shipped.

The default `runtime` target, which builds the SPA and the binary inside Docker, is for local
builds and `make rust-test-image`; neither CI nor the release builds it. The accuracy harness is not
part of CI: it is dispatched by hand before a release ([How to Release](#how-to-release)).

What only the release can see is what changed since: a vulnerability published after CI ran (the
scan and the audit run at release time for that reason), a newer rebuild of the base tag, and a
broken image build, which the smoke test on the release's own build catches before the tag.

## The Scan Gate

The gate (`trivy-gate`, on both platform images) fails on a `HIGH` or `CRITICAL` vulnerability
**with a fix upstream**; the findings with no fix yet are left out (`--ignore-unfixed`), since
nothing in this repository can fix them. Trivy is always its latest release, never pinned, so every
scan runs the newest checks (`meta/tests/toolchain.rs` fails on a Trivy pin); its vulnerability
database is fetched at run time, which is the point of scanning at release time.

The base's findings count the same as the image's own: a fixable finding in `dhi.io/static` fails
the release too. Its fix is usually dhi.io's next rebuild of the tag, which the next release picks
up by itself, or a newer tag, which Dependabot proposes; until it ships, a reviewed entry in
[`.trivyignore.yaml`](../.trivyignore.yaml) is the only way past the gate, scoped to the paths or
purls it was found in, with a statement saying why and an expiry date Trivy enforces. When an entry
expires, bump what carries the fix if it is out, otherwise extend the date with a fresh reason.

The binary is not built with `cargo auditable`, so Trivy cannot see its crates, nor the SPA's npm
packages; `make audit-deps` (cargo-deny and `npm audit`), in the `audit` job and CI, is the check
for them.

## Dry Runs

`dry_run: true` rehearses a fresh release: it resolves the version and decides the mode (so it
stops, like a real run would, when the version is held or needs a human), then runs the CI gate,
fresh steps 1 to 7 (the smoke tests, the scans and the wait for the audit included), and exercises
step 9 by copying the index to a **second job-local registry** instead of GHCR, checking that the
copy keeps its digest and one attestation manifest per platform. It also runs the binary
attestation check as a rehearsal, but attests nothing. It pushes no tag and publishes nothing. A
dry run of a version whose image already exists stops at step 7.

The job summary shows the version, the previous tag, whether the version was explicit, the mode a
real run would take, the toolchains, the index and platform digests, the base each platform was
built on and the checksums; the binaries and `checksums.txt` are uploaded as the workflow artifact
`dry-run-<tag>-<attempt>`. A dry run with no version is also the quickest way to see what version
the commits would produce.

## Tags

| Image tag | Points to | Moves on |
| --- | --- | --- |
| `ghcr.io/leinardi/bitgauge:X.Y.Z` | that release | never |
| `ghcr.io/leinardi/bitgauge:X` | the latest release of major `X` | every release of major `X` |
| `ghcr.io/leinardi/bitgauge:latest` | the latest release | every release |

The git tag carries a `v` prefix (`vX.Y.Z`); image tags do not. Only GHCR is published. A version
tag, git or image, never moves once it is set; `X` and `latest` move only to a higher version.
Pinning `X.Y.Z` or a digest gives a fixed image; a base-image fix arrives as a new version, so
following `X` or `latest`, or upgrading, is the way to receive it.

## Recovering a Failed Release

Nothing needs deleting: a failed run either pushed no tag, or pushed one that a re-run can finish.

- **Failed before the tag was pushed** (the CI gate, a build, smoke test, scan, audit or gate
  failure): nothing is published. Fix the cause on `main` and dispatch again.
- **Failed after the tag was pushed** (copy, signing, attestation or the GitHub release): a
  recovery has to run on the tagged commit, because that is the only commit the tag check accepts
  for an existing tag. Two ways get there:
  - **"Re-run all jobs"** on the failed run. This always works: a re-run keeps the original run's
    commit and inputs, whatever has been merged since, and that commit's CI already passed. Use
    "Re-run all jobs", not "Re-run failed jobs", unless `audit` itself failed: the release job
    accepts only an `audit` of its own attempt (`require-job-success` never trusts an earlier
    attempt's pass), and "Re-run failed jobs" does not re-run an `audit` that passed, so the
    release would wait for it until the step times out.
  - **A fresh dispatch with the same version, given explicitly**, while `main` still points at the
    tagged commit. Once anything has been merged after it, the version step refuses, and the re-run
    above is the way.

`release-mode` then decides **per platform**, so the image binary and the release asset of a
platform never diverge. "Published" means the image (or its platform manifest) is on GHCR, or the
release, draft or not, carries the asset; each must be attested by this workflow for this commit,
and the image signed by it too, or the run stops.

| Published for a platform | The binary comes from | What happens |
| --- | --- | --- |
| Image and asset | the image | they must be the same bytes, or the run stops |
| Image only | the image | it is extracted, attested and uploaded as the asset |
| Asset only | the asset | it is downloaded and verified, and the image is built with it |
| Neither | a rebuild | it is built now, with the recorded toolchains |

- **Recovery, reuse**, when `:X.Y.Z` exists and is attested and signed by this workflow for this
  commit: nothing is built; missing assets are extracted from the image. The image is scanned, and
  findings are reported as warnings: it is already published and immutable, and failing would only
  leave the release assets unfinished.
- **Recovery, publish**, when the tag exists and `:X.Y.Z` does not: the image is built from the
  published binaries where there are any and rebuilt ones for the other platform, then
  smoke-tested, scanned, copied, checked, attested, signed and tagged. Untagged digests an earlier
  attempt left are inert and ignored. If the scan now fails, because a fixable vulnerability was
  published since, **the version is abandoned**: its tag stays, with no image, and the fix ships as
  a higher version.

A published image that lacks a shipped platform stops the run: a manifest list cannot gain a
platform without changing its digest. A tag whose annotation does not record the toolchains
cannot be recovered either (`toolchain-recover` and `release-mode` fail closed on it); every tag
this workflow pushes records them.

The workflow artifacts carry the run attempt in their names (`binaries-<tag>-<attempt>`,
`dry-run-<tag>-<attempt>`), because a re-run stays inside the same workflow run and
`upload-artifact` refuses to overwrite the first attempt's upload.

- **Published release is broken** (the wrong commit, a bad build): do not move or delete anything.
  Fix forward with `X.Y.(Z+1)`.
- **A stop row of the mode table** is for a human: something outside this workflow holds the
  version. Find out where the image, the asset or the release came from, and release a higher
  version.

## Recovery Guarantees

One rule governs every publishing step: **a published artifact is never replaced, and it is reused
only once it is proven to be this run's**, never because something with the right name exists.

- **The image.** A new image is copied to GHCR by digest with no tag, attested and signed, and only
  then tagged `X.Y.Z`, so a version tag only ever points at a digest this workflow tested, scanned,
  attested and signed. A reused image must pass

  ```bash
  gh attestation verify oci://ghcr.io/leinardi/bitgauge@<digest> --repo leinardi/bitgauge \
    --signer-workflow leinardi/bitgauge/.github/workflows/release.yaml \
    --source-ref refs/heads/main --source-digest <commit>
  ```

  and carry this workflow's own cosign signature (identity
  `https://github.com/leinardi/bitgauge/.github/workflows/release.yaml@refs/heads/main`, issuer
  `https://token.actions.githubusercontent.com`), both checked by `release-mode` first. The
  workflow signs with cosign v3, which stores the signature as a Sigstore bundle in an OCI 1.1
  referring artifact, so verifying it by hand needs cosign v3, or v2.6 or later with
  `--new-bundle-format`.
- **The release assets.** The release is created as a draft if it does not exist, with the
  toolchains and the base digests above the generated notes. Each expected asset (the two binaries
  and `checksums.txt`) is inventoried one by one: a present asset is downloaded and compared by
  SHA-256 with this run's (the rebuilt or verified binary), and with the published `checksums.txt`
  when that is present, and a mismatch fails the run; a missing asset is uploaded, never with
  `--clobber`. An asset that is not expected fails the run. `checksums.txt` is regenerated over the
  final binaries, and must equal a published one.
- **The binary attestations.** The binaries are the same bytes on every run, so an attestation an
  earlier run made for one is reused, not duplicated. `binary-attestation-status` looks up each
  binary's SHA-256: one with no attestation is attested; one with an attestation must pass
  `gh attestation verify` with the same repository, signer workflow, source ref and commit as the
  image, and is then left alone. Any other answer stops the run before the release is drafted, for
  a human.
- **The latest pointers.** `latest`, `X` and the GitHub "Latest" marker move only if the version is
  still the highest when that pointer is moved: the highest remote tag is read again immediately
  before retagging the image, and again immediately before the release is published out of draft.

The last one is **best-effort, not atomic**. GHCR tags and GitHub releases cannot be updated
together, so a tag created outside this workflow in the seconds between the two moves can still
leave them disagreeing (runs of this workflow cannot race each other, because of the concurrency
group). After both moves, the run reads the highest remote tag once more and warns rather than
moving anything back, because it cannot know that the other version's image exists or can be
trusted. Re-dispatch the higher version, whose own late checks repoint them, or retag by hand after
checking the digest you point at:

```bash
IMAGE=ghcr.io/leinardi/bitgauge
DIGEST=sha256:...   # the digest of the image that should be latest
gh attestation verify "oci://$IMAGE@$DIGEST" --repo leinardi/bitgauge \
  --signer-workflow leinardi/bitgauge/.github/workflows/release.yaml --source-ref refs/heads/main
docker buildx imagetools create -t "$IMAGE:latest" -t "$IMAGE:<major>" "$IMAGE@$DIGEST"
```

## Scheduled Scan

A release is scanned once, when it is built, but vulnerabilities keep being published.
[`scheduled-scan.yaml`](../.github/workflows/scheduled-scan.yaml) runs `make audit-deps` over
`main`'s dependencies and, once releases exist, resolves `:latest` to its index digest once and
scans each platform image by its own digest with the release's gate (`trivy-gate`, the latest
Trivy, the same ignore file). Any finding fails the run. The published image is immutable, so the
fix is a new release (for a base finding, on the base tag's newer rebuild), or a reviewed entry in
the ignore file. It runs every Monday at 06:17 UTC, and by hand.

## What the Workflows Trust

**Every action is pinned to a full commit SHA**, with the version in a trailing comment, in every
workflow, reusable and warm-up workflows included. A tag is a mutable pointer, and an action that
moves, or whose repository is compromised, would execute inside the release job, which holds
`contents: write`, `packages: write` and an OIDC identity. A SHA cannot be moved. Dependabot's
`github-actions` ecosystem updates the pins and rewrites the comment. The one tool deliberately not
pinned is Trivy, which `trivy-gate` installs at its latest release. svu, ShellCheck, zig,
cargo-zigbuild and cargo-deny are pinned with their checksums inside the gh-composite-actions that
install them.

**Every image the release job runs is pinned by digest, except the `dhi.io` bases**: the job-local
registry and skopeo in the workflow's `env`, the QEMU emulator, and the
`# syntax=docker/dockerfile:…` BuildKit frontend in the Dockerfile. Bump them by hand: resolve the
new index digest with `docker buildx imagetools inspect <image>:<tag>` and replace the tag and the
digest together. **The `dhi.io` bases are pinned by an explicit tag, deliberately not by digest**,
because `dhi.io` republishes its tags with security fixes: `dhi.io/node` and `dhi.io/rust` for the
default target's web and build stages and `dhi.io/static` for the shipped base, each in one literal
`FROM <image>:<tag>` (`meta/tests/dockerfiles.rs`, `check-pinned-bases`). Each release records the
base digest it shipped ([What CI Proves](#what-ci-proves)).

**The binaries are built outside Docker, once.** The release's `rust-release-binaries` gets zig and
cargo-zigbuild from gh-composite-actions' `setup-zigbuild`, at the versions `.mk/rust-release.mk`
pins, Rust from `rust-toolchain.toml` and Node from its major, or, on a recovery, the releases the
tag records. The image's `prebuilt` target never runs the web or build stages: it COPYs the
binaries, so `dhi.io/node` and `dhi.io/rust` are not part of a release at all.

**Workflow tokens are read-only by default.** Every workflow sets `permissions: contents: read` at
the top, and only the jobs that need more say so: the release job adds `contents: write`,
`packages: write`, `id-token: write`, `attestations: write` and `actions: read`, in the `release`
environment; `ci-green` adds `actions: read`; the reviewdog jobs in `ci.yaml` add
`pull-requests: write`; the scheduled scan's image job adds `packages: read`; the warm-ups' prune
jobs add `actions: write`. No checkout keeps credentials: the release passes the token to the git
commands that need it, step by step.

**Caches.** The release's Rust build cache is its own (`prefix-key: release`) and its npm cache is
setup-node's, both restored and saved only by this workflow, which runs on `main` only. CI's Rust
caches (`shared-key: ci`) are saved only on `main`, by one job per key, so no pull request can seed
a cache the release reads; the web cache (ESLint, vue-tsc and npm's download cache) is saved only by
the main-only web warm-up, the pre-commit cache only by its warm-up, and the Playwright browsers only
from `main`. A cache only speeds the build: the binaries come from the lockfiles and the remapped,
pinned toolchains either way, and a recovery checks them by SHA-256 against what was published. No
image build uses a layer cache.

A SHA pin fixes only the top-level ref, so the actions and reusable workflows the owner maintains
(`leinardi/gh-composite-actions`, `leinardi/gha-pre-commit-reviewdog-actions`,
`leinardi/gh-reusable-workflows`) pin what they run too. The warm-up workflows matter more than they
look: every step in a job also gets the Actions cache token, which can write any cache key, and the
warm-ups run on `main`, so they write into the `main` cache scope. Keep the nested pins current in
those repositories, and bump the pins here when they release.

## Dependabot

Monthly update pull requests for five ecosystems, each with a seven-day cooldown:

| Ecosystem | Scope | Commit prefix |
| --- | --- | --- |
| `cargo` | dependencies (the `meta` and `testenv` crates' included) in one group, dev-dependencies in another | `fix(deps)`; dev-dependencies `chore(deps)` |
| `npm` (`web/`) | runtime dependencies in one group, devDependencies in another | `fix(deps)`; devDependencies `chore(deps)` |
| `docker` | stage image tags in the Dockerfile | `fix(deps)`: the base ships in the image |
| `github-actions` | actions pinned by commit SHA | `chore(deps)` |
| `pre-commit` | hook revisions in `.pre-commit-config.yaml` | `chore(deps)` |

One grouped pull request carries a single prefix, so the production and development groups are
separate: mixing them would release a binary that did not change. Every update passes the same CI as
any other pull request. Docker tag updates pull from `dhi.io`, so Dependabot needs its own copy of
the `dhi.io` token (see the setup below).

## Required Checks and Fork Pull Requests

The rulesets are managed as code in
[`leinardi/gh-leinardi-iac`](https://github.com/leinardi/gh-leinardi-iac), in the `repo_bitgauge`
module of `stacks/github-repos/repos.tf`, never by hand or with `gh api`: the ruleset on `main`
(pull requests only, no force push, no deletion) and the immutable `v*` tag ruleset. A change to
either is a pull request there.

The one required check is `ci-result`, set there as `default_branch_required_checks =
["ci-result"]`. It needs every other job of `ci.yaml` (`pre-commit-all`, `conventional-commits`,
`repo-gates`, `rust`, `web`, `audit`, `credentials`, `image` and `e2e`; the accuracy harness is
dispatched by hand) and fails unless each one succeeded, so a new job becomes required by joining
`ci-result`'s `needs`, not the ruleset. GitHub counts a skipped required job as passing, which is
why the jobs themselves are not listed. The reviewdog annotation jobs are not needed by
`ci-result`; they duplicate `pre-commit-all` as inline comments. The release does not depend on the
rule: it reads `ci-result` of the commit's `ci.yaml` push run itself (`require-ci-green`).

Once the ruleset is applied, open one pull request and confirm the required check reports under
exactly the name `ci-result`. A required check that never reports blocks every merge.

Jobs that pull `dhi.io` images (the image job, the accuracy harness, release and the scan's image
job) need a **trusted run**: a push to `main`, a schedule or dispatch, a pull request from a branch
of this repository, or Dependabot. A pull request from a fork gets no secrets, so the image job is
skipped with a notice, and `ci-result` fails on a fork pull request whose image job was skipped:
no gate passes on nothing. The image job has no path filter, so this applies to every fork pull
request, documentation-only ones included. `pull_request_target` is never used.

The only merge path for a fork pull request is then a **replacement pull request**: a maintainer
pushes the fork's commits unchanged (authorship preserved) to a branch of this repository, opens a
pull request that references the original, merges it once it is green, and closes the fork pull
request with a link. This path is **unverified** until it has been tested with a real fork from a
second account.

## One-Time Setup

Do these before the first dispatch, dry runs included. They need a **public repository**, because
several pieces are limited on a private one:

- Environments, environment secrets, deployment branch rules and rulesets need GitHub Pro, Team or
  Enterprise on a private repository. Without them the `release` environment and the tag and branch
  rules are not enforced.
- Artifact attestations on a private repository need GitHub Enterprise Cloud. Without them the
  image attestation of fresh step 10, the binary attestations and the `gh attestation verify`
  checks behind every recovery all fail.

1. **The `release` environment**, restricted to `main` with a deployment branch rule, as a
   server-side second line of defense behind the `guard` job. Add required reviewers too if a
   release should wait for a human. A run that references a missing environment creates it with no
   protection rules.
2. **The `dhi.io` token.** The prebuilt image's base, `dhi.io/static`, cannot be pulled without a
   login, and the default target's stages pull `dhi.io/rust` and `dhi.io/node` too. The user name
   is `leinardi`, written in the workflows and in `.github/dependabot.yml`; use a pull-only token as
   `DHI_TOKEN` in three places:
   - the **release** job: an Actions secret, best **on the environment**, so only a job that passed
     the environment's rules reads it;
   - CI's `image` job and `harness.yaml`, which run outside the environment: a repository Actions
     secret;
   - **Dependabot**, which does not see Actions secrets: both to update the bases (the `dhi`
     registry in `.github/dependabot.yml`) and for CI on its pull requests.

   ```bash
   gh secret set DHI_TOKEN
   gh secret set DHI_TOKEN --env release
   gh secret set DHI_TOKEN -a dependabot
   ```

   The `DHI_USERNAME` variable and secret are no longer read.
3. **Workflow permissions.** Every workflow is `contents: read` at the top, and the default
   workflow token permission stays read-only ([What the Workflows Trust](#what-the-workflows-trust)).
4. **Immutable tags.** A ruleset on `v*` tags with no update, no deletion and no bypass, managed in
   `gh-leinardi-iac` ([required checks](#required-checks-and-fork-pull-requests)).
5. **Branch protection** on `main`: pull requests only, and the required `ci-result` check, managed
   in `gh-leinardi-iac` ([required checks](#required-checks-and-fork-pull-requests)).
6. **Dependabot** enabled with the configuration above, and **private vulnerability reporting**
   enabled for [SECURITY.md](../SECURITY.md).
7. **GHCR package visibility (after the first release).** The first release creates
   `ghcr.io/leinardi/bitgauge`, already linked to the repository because a repository workflow
   pushed it. New packages are private, so set its visibility to public; until then nobody else can
   pull the image.

### Bumping the Rust Toolchain

One exact Rust release builds everything: `rust-toolchain.toml` (which the workflows install with
`rustup toolchain install`, so they name no release of their own), the Cargo `rust-version`, the
`dhi.io/rust:<version>-debian13-dev` tag and `ARG RUST_VERSION` of the Dockerfile's build stage, and
`.mk/rust-release.mk`'s `rust-std` release; `meta/tests/toolchain.rs` fails when they differ, patch
included. Dependabot ignores the `rust` image on purpose: the build stage adds each musl target by
unpacking `rust-std-<version>-<triple>.tar.xz` and checking it against a sha256 written in the
Dockerfile and `.mk/rust-release.mk`, and those archives must be the image's exact release. A bump
is therefore one hand-made pull request that moves them all together, with the two `rust-std`
sha256s.

zig and cargo-zigbuild follow the same rule between `.mk/rust-release.mk`, the Dockerfile and the
`setup-zigbuild` steps of `ci.yaml` and `release.yaml` (their `zig-version` and
`cargo-zigbuild-version` inputs), checked by the same meta-test. `setup-zigbuild` checks the
archives it downloads against its `zig-sha256` and `cargo-zigbuild-sha256` inputs, whose defaults
are its default versions' digests, so a version bump passes the new digests to it too.
