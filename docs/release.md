# Release

How a BitGauge release is versioned, built and published, what to do when a release fails halfway,
and what has to be set up by hand for all of it to hold. The workflow is not written yet:
`release.yaml` lands once the image and web build gates are active, and its shape is specified here
and in [build-packaging.md §4](features/technical-stack/build-packaging.md#4-ci-workflows).

> [!IMPORTANT]
> **Provisional: the release process must be revised before the repository goes public.** It
> follows the release model of swarm-scheduler-exporter, which has shipped releases with it, as
> ported through Runhold, and was chosen while the repository is private; the
> [going-public checklist](engineering/going-public.md#1-revise-the-release-model) revisits it
> before the first public release.

**There has been no release yet.** Before the first dispatch, dry runs included, do the
[one-time setup](#one-time-setup).

## What a Release Produces

- Two static binaries, `bitgauge-linux-amd64` and `bitgauge-linux-arm64`, built with
  `CGO_ENABLED=0`, `-trimpath` and `-buildvcs=false`, with the version, commit and commit date
  compiled into `internal/buildinfo` and the SPA embedded. A `checksums.txt` file covers both. All
  three files are attached to the GitHub release, and each binary has a build provenance
  attestation made by the release workflow
  ([attestations](https://docs.github.com/actions/security-guides/using-artifact-attestations)).
- One multi-arch (`linux/amd64`, `linux/arm64`) image, `ghcr.io/leinardi/bitgauge:X.Y.Z`, with an
  SPDX SBOM and a `mode=max` SLSA provenance attestation for every platform image, a build
  provenance attestation, and a keyless [cosign](https://docs.sigstore.dev/) signature on the image
  digest, made with the release workflow's own GitHub OIDC identity; no signing key exists
  anywhere. Both platform images were scanned with [Trivy](https://trivy.dev/) before the version
  was tagged and had no `HIGH` or `CRITICAL` vulnerability outside the `.trivyignore` at the
  repository root.
- The moving image tags `X` and `latest` of [Tags](#tags), and the GitHub "Latest" release marker,
  when the version is the highest released one.
- Release notes generated by GitHub from the merged pull requests.

[SECURITY.md](../SECURITY.md#verifying-a-release) shows how to verify an image or a binary.

## How to Release

1. Make sure `main` is green and that the manual floor and ceiling tiers of the accuracy harness,
   and the real Safari and iOS checks, have passed for this commit and are recorded in
   [engineering/](engineering/README.md). A release is blocked until they have
   ([features/technical-stack/testing.md §6](features/technical-stack/testing.md#6-ci-placement)).
2. Run the **Release** workflow (`release.yaml`) from the Actions tab, or
   `gh workflow run release.yaml`, on `main`. It is `workflow_dispatch` only and takes two inputs:
   - `version`: optional, `X.Y.Z` or `vX.Y.Z`. Left empty, the version is derived from the
     commits since the last release (see [Versioning](#versioning)). The first release needs it,
     since there is no tag to derive from. Give it explicitly to force a version, or to recover a
     failed run with a fresh dispatch (see
     [Recovering a Failed Release](#recovering-a-failed-release)).
   - `dry_run`: boolean, default `false`. See [Dry Runs](#dry-runs).

Nobody creates or pushes a tag by hand: the workflow builds, scans and verifies everything first,
and pushes the tag itself only then (see
[Why the Build Happens Before the Tag](#why-the-build-happens-before-the-tag)).

**One release runs at a time.** `release.yaml` takes the `release` concurrency group with
`cancel-in-progress: false`, so a second dispatch queues behind the first instead of racing it. Two
runs in flight together would each check their version against the same latest tag, both pass, and
then publish in whatever order they finished, and a lower version landing last would take `latest`
with it. A run that has started is never cancelled part-way through publishing.

## Versioning

Semantic versioning, derived from
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) by
[`svu`](https://github.com/caarlos0/svu):

- `feat` is a minor.
- `fix` is a patch.
- `!` before the colon, or a `BREAKING CHANGE:` footer, is a major. Before `1.0.0`, `svu` turns a
  breaking change into `1.0.0` straight away; while BitGauge is on `0.x`, release a breaking change
  with an explicit version if it should stay on `0.x`.

Everything else (`build`, `chore`, `ci`, `docs`, `perf`, `refactor`, `revert`, `style`, `test`)
bumps nothing, and the highest bump among the commits wins. A change users should receive in the
binary, the image or the web app is committed as `fix` or `feat`, even when it is a performance
improvement, a refactor or a revert; `perf`, `refactor`, `style` and `revert` are for changes
deliberately not meant to trigger a release, and a revert of a shipped `feat` or `fix` is itself a
`fix`. `svu` matches `feat`/`fix` anywhere in the subject, so `prefix:` counts as `fix:`. Pull
requests land as merge commits, so every commit counts, not only the pull request title
([AGENTS.md](../AGENTS.md#commit-messages)). When no commit since the last release is a `feat`, a
`fix` or a breaking change, a run with no version **fails** with
"No feat/fix or breaking-change commit since `<tag>`, so there is nothing to bump. Re-run with an
explicit version to force one." The one exception is a recovery: when `svu next` answers a strict
tag that already sits on `HEAD`, the run treats it as a recovery of that version, not as "nothing
to bump", so re-running a failed run that derived its version works.

Dependabot's Go module and runtime npm updates are committed as `fix(deps)`, so a dependency bump
alone is enough for a patch release. Its `docker`, `github-actions` and `pre-commit` updates, and
npm devDependency updates, stay `chore(deps)` and bump nothing. **A base-image digest bump that
carries a security fix therefore needs an explicit version to ship**: there is no rebuild of a
published version, and the [scheduled scan](#scheduled-scan) is what says one is needed.

Only strict `vMAJOR.MINOR.PATCH` git tags are releases: `v`, then three dot-separated numbers, each
`0` or a number with no leading zero, and nothing after them, which is
`^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` (`RELEASE_TAG_REGEX` in the workflow). An
explicit version must match too, so `01.2.3`, `1.02.3`, `1.2.3-rc.1`, `1.2.3+meta`, `1.2` and
`v1.2.3.4` are refused. Every lookup (the current, the latest and the previous release, the
recovery check, and the remote checks before tagging and before moving the pointers) filters the
full tag list through that regex, never a glob, so pointer tags such as `latest` or `v1`,
pre-release, build-metadata and malformed tags can never become the current version or stop the
version from resolving.

`svu` is given the exact tag to count from: the highest strict tag reachable from `HEAD`, passed
literally as `--tag.pattern`. `svu` matches that option as a glob against every tag, and a glob
such as `v[0-9]*.[0-9]*.[0-9]*` also matches `v1.2.3-rc.1`; a strict tag holds only `v`, digits
and dots, so as a glob it matches that one tag and nothing else. When no strict tag is reachable
from `HEAD`, a run with no version fails and asks for an explicit one rather than letting `svu`
guess.

A new version must be higher than every version already released. **A pushed tag is never moved,
deleted or reused**: an immutable-tags ruleset forbids it, and the workflow never needs it, because
the tag is pushed only after everything that can fail without a tag has succeeded. The only
version a run may reuse is the one it is recovering, which is exactly that tag already sitting on
`HEAD`. A branch whose history does not contain the highest release derives from an older base and
fails that check; the failure names the out-of-history tag, and an explicit version higher than it
is the way out.

### Stray Local Tags

CI fetches only the tags on `origin`, so it is unaffected by anything in a local clone. A local
`svu next`, or the version step run by hand, is not: a strict tag that exists only locally is read
like any other. Remove tags that are not on `origin` before reasoning about versions locally:

```bash
git fetch --prune --prune-tags origin   # drops local tags that origin does not have
```

## Why the Build Happens Before the Tag

The `v*` tags are protected by an immutable-tags ruleset (no update, no deletion, no bypass), so a
"delete the tag on failure" cleanup cannot exist: it would fail every time, and a failed release
would leave a tag nobody can remove. Everything that can fail without a tag happens before the tag
exists, and everything after it can be finished by a re-run on the tagged commit (see
[Recovering a Failed Release](#recovering-a-failed-release)).

Every run starts the same way:

1. **Refuse anything but `main`.** The `guard` job fails, rather than skips, when `github.ref` is
   not `refs/heads/main`, and every other job waits on it. `workflow_dispatch` lets the caller pick
   any branch, and the release job holds `contents: write`, `packages: write` and an OIDC
   identity.
2. **Verify.** `go-test` and `web` (the same reusable workflows `ci.yaml` calls, run again at this
   commit, so a release never depends on which pull request last ran CI) and `audit`
   (`make audit-deps`). Then the `release` job runs, in the `release` environment, with
   `contents: write`, `packages: write`, `id-token: write` and `attestations: write`.
3. **Resolve the version**, as in [Versioning](#versioning).
4. **Check the tag.** If `refs/tags/vX.Y.Z` already exists on the remote, the run continues only
   when it points at `HEAD`, as a recovery; pointing anywhere else is a hard failure. A new tag is
   created **locally only**, annotated with the exact Go and Node versions the binaries are built
   with (`Go: go1.26.N`, `Node: v24.N.N`). `.go-version` names a Go line and the web app is built
   with a Node major, and both resolve to the newest patch on the day of the run; a recovery reads
   the annotation and switches to the recorded versions before building, which is what makes its
   binaries byte-identical to the first attempt's.
5. **Decide the mode**, fail-closed, from two lookups made before anything is built or pushed: the
   git tag on the remote (the step above) and the image `ghcr.io/leinardi/bitgauge:X.Y.Z`. Only
   "not found" counts as absent; an authentication or network error stops the run, because reading
   it as "absent" could push a tag or an image over something the run could not see.

   | Git tag | Image `:X.Y.Z` | Mode |
   | --- | --- | --- |
   | absent | absent | **Fresh** |
   | absent | present | **Stop before tagging**: the version is held by an image |
   | on this commit | present, attested by this workflow for this commit | **Recovery, reuse** |
   | on this commit | present, not attested by this workflow | **Stop: needs a human** |
   | on this commit | absent | **Recovery, publish** |

   A tag on another commit already failed the step above.

A **fresh** release then runs these steps. They are numbered because the other modes are defined by
them:

1. **Start a registry inside the job** (`registry:3.1.2`, pinned by digest) and give Buildx the host
   network, so it can push there.
2. **Build** the web app, then the two static binaries and `checksums.txt`.
3. **Build the image once**, for both platforms, with one `docker/build-push-action` run: SBOM,
   `mode=max` provenance, pushed by digest to the job-local registry, after logging in to `dhi.io`
   for the build stages. There is no other image build: what is scanned is what is published. Every
   layer is recompressed as gzip, because the `dhi.io` base layers are zstd, and for a zstd image
   skopeo rewrites the index entries with a compression annotation, which the digest-preserving
   copy of step 7 then refuses.
4. **Scan** both platform images, each by its own digest, with
   `trivy image --scanners vuln --severity HIGH,CRITICAL --exit-code 1 --platform <platform>`. A
   finding fails the run with no tag anywhere. `--ignore-unfixed` is not used: a vulnerability with
   no fix yet still blocks, unless it is accepted in `.trivyignore` with a reason and an expiry
   date.
5. **Gate the tag.** The highest released version is read again, from the remote, because a tag can
   arrive from outside the workflow while it builds; a fresh release that is no longer the highest
   fails with nothing pushed. Then the image `:X.Y.Z` is checked absent with the same fail-closed
   lookup as the mode decision: the tag must never point at a version an image already holds.
6. **Push the tag**: the point of no return.
7. **Copy to GHCR, untagged**: `skopeo copy --all --preserve-digests` from the job-local registry to
   `ghcr.io/leinardi/bitgauge@<digest>`, with skopeo run from an image pinned by digest. The index
   keeps its digest, and its SBOM and provenance manifests come along.
8. **Check, attest, sign.** The index GHCR serves under the digest is hashed and must equal the
   scanned digest; then the digest is attested and signed (`cosign sign --yes`).
9. **Tag the image** `X.Y.Z`, after checking once more that the tag is absent: a version tag that
   appeared since is never overwritten.

The binary attestations, the release assets and the latest pointers follow, in every mode, as
described under [Recovery Guarantees](#recovery-guarantees).

Everything stamped into an artifact comes from the commit rather than from the clock: the version,
a fixed seven-character commit prefix, the commit date as the build date, and the commit time as
BuildKit's `SOURCE_DATE_EPOCH`. The binaries are built with `-trimpath` and the exact toolchains of
step 4 above, so a re-run of the same commit produces the same bytes, which is what lets a recovery
check published assets by SHA-256. The image is not byte-reproducible: its provenance records the
build itself, so two builds of the same commit have different index digests. That is why a
recovery never compares a rebuilt index with a published one. The image's base images are pinned by
digest in `deployments/docker/Dockerfile`, and Dependabot moves the pins forward through reviewed
pull requests.

## Dry Runs

`dry_run: true` rehearses a fresh release: it resolves the version and decides the mode (so it
stops, like a real run would, when the version is held by an image or needs a human), then runs
fresh steps 1 to 5, and exercises step 7 by copying the index to a **second job-local registry**
instead of GHCR. The copy is checked the same way: the copied index must hash to the scanned
digest, and must still carry one attestation manifest per platform. It also runs the binary
attestation check as a rehearsal, but attests nothing. It pushes no tag and publishes no image and
no release.

The job summary shows the version, the previous tag, whether the version was explicit, the mode a
real run would take, the toolchain versions, the index digest, the scanned platform digests and
the artifact list; `dist/` is uploaded as the workflow artifact `dry-run-<version>-<attempt>`. A
dry run with no version is also the quickest way to see what version the commits would produce.

## Tags

| Image tag | Points to | Moves on |
| --- | --- | --- |
| `ghcr.io/leinardi/bitgauge:X.Y.Z` | that release | never |
| `ghcr.io/leinardi/bitgauge:X` | the latest release of major `X` | every release of major `X` |
| `ghcr.io/leinardi/bitgauge:latest` | the latest release | every release |

The git tag carries a `v` prefix (`vX.Y.Z`); image tags do not. Only GHCR is published. A version
tag, git or image, never moves once it is set; `X` and `latest` move only to a higher version.
Pinning `X.Y.Z` or a digest gives a fixed image; a base-image fix arrives as a new version, so
following `X` or `latest`, or upgrading, is the way to receive it.

## Recovering a Failed Release

Nothing needs deleting: a failed run either pushed no tag, or pushed one that a re-run can finish.

- **Failed before the tag was pushed** (a test, build, scan or gate failure): nothing is
  published. Fix the cause on `main` and dispatch again.
- **Failed after the tag was pushed** (copy, signing, attestation or the GitHub release): a
  recovery has to run on the tagged commit, because that is the only commit the tag check accepts
  for an existing tag. Two ways get there:
  - **"Re-run failed jobs"** (or "Re-run all jobs") on the failed run. This is the default, and it
    always works: a re-run keeps the original run's commit and inputs, whatever has been merged
    since. A run that derived its version works too.
  - **A fresh dispatch with the same version, given explicitly.** A dispatch always runs on the
    current `main` head, so this works only while `main` still points at the tagged commit. Once
    anything has been merged after it, the version step and the tag check both refuse, and the
    re-run above is the way.

Either way the tag check sees the tag on `HEAD`, the binaries are rebuilt with the toolchains
recorded in the tag, and the mode decision picks one of two recoveries:

- **Recovery, reuse**, when `:X.Y.Z` exists and is attested by this workflow for this commit. The
  published image is verified by its attestation and its signature and reused by digest: nothing is
  built, copied or attested again, and it is never compared with a rebuilt index. Its platform
  images are scanned, and findings are reported as warnings rather than failures: the image is
  already published and immutable, and failing would only leave the release assets unfinished.
- **Recovery, publish**, when the tag exists and `:X.Y.Z` does not: the earlier run failed between
  pushing the tag and tagging the image. Fresh steps 1 to 4 and 7 to 9 run: a new build, scanned,
  copied, checked, attested, signed and tagged. Untagged digests an earlier attempt left are inert
  and ignored. If the scan now fails, because a vulnerability was published since, **the version is
  abandoned**: its tag stays, with no image, and the fix ships as a higher version.

The workflow artifacts carry the run attempt in their names (`binaries-<version>-<attempt>`,
`dry-run-<version>-<attempt>`), because a re-run stays inside the same workflow run and
`upload-artifact` refuses to overwrite the first attempt's upload.

- **Published release is broken** (the wrong commit, a bad build): do not move or delete anything.
  Fix forward with `X.Y.(Z+1)`.
- **A stop row of the mode table:** something outside this workflow holds the version. **The
  version is held by an image with no tag:** nothing was pushed; release a higher version. **The
  tag is on this commit but the image is not attested by this workflow:** nothing more is published
  and the image tag is never overwritten; find out where the image came from, and release a higher
  version.

## Recovery Guarantees

One rule governs every publishing step: **a published artifact is never replaced, and it is reused
only once it is proven to be this run's**, never because something with the right name exists.

- **The image.** A new image is copied to GHCR by digest with no tag, attested and signed, and only
  then tagged `X.Y.Z`, so a version tag only ever points at a digest this workflow scanned, attested
  and signed. An existing `:X.Y.Z` is reused only after

  ```bash
  gh attestation verify oci://ghcr.io/leinardi/bitgauge@<digest> --repo leinardi/bitgauge \
    --signer-workflow leinardi/bitgauge/.github/workflows/release.yaml \
    --source-ref refs/heads/main --source-digest <commit>
  ```

  binds it to this repository, this workflow and this commit.
- **The signature.** A signature counts only when it matches this workflow's identity,
  `https://github.com/leinardi/bitgauge/.github/workflows/release.yaml@refs/heads/main`, and the
  issuer `https://token.actions.githubusercontent.com`. A reused image must already carry one,
  since the version tag is only ever added after signing; one without it stops the run for a
  human. The workflow signs with cosign v3, which stores the signature as a Sigstore bundle in an
  OCI 1.1 referring artifact, so verifying it by hand needs cosign v3, or v2.6 or later with
  `--new-bundle-format`.
- **The release assets.** The release is created as a draft if it does not exist. Each expected
  asset (the two binaries and `checksums.txt`) is inventoried one by one: a present asset is
  downloaded and compared by SHA-256 with this run's build, and with the published `checksums.txt`
  when that is present, and a mismatch fails the run; a missing asset is uploaded, never with
  `--clobber`. An asset that is not expected fails the run. A partial upload is therefore finished,
  never overwritten.
- **The binary attestations.** The binaries are rebuilt byte-identically on every run, so an
  attestation an earlier run made for one is reused, not duplicated.
  `.github/scripts/binary-attestation-status.sh` looks up each binary's SHA-256: one with no
  attestation is attested; one with an attestation must pass `gh attestation verify` with the same
  repository, signer workflow, source ref and commit as the image, and is then left alone. Any
  other answer (an attestation that fails that check, an HTTP error other than the "no
  attestations" 404, a network error, a body that does not parse) stops the run before the release
  is drafted, for a human. The script's tests run in CI (`release-scripts`).
- **The latest pointers.** `latest`, `X` and the GitHub "Latest" marker move only if the version is
  still the highest when that pointer is moved: the highest remote tag is read again immediately
  before retagging the image, and again immediately before the release is published out of draft.

The last one is **best-effort, not atomic**. GHCR tags and GitHub releases cannot be updated
together, so a tag created outside this workflow in the seconds between the two moves can still
leave them disagreeing (runs of this workflow cannot race each other, because of the concurrency
group). After both moves, the run reads the highest remote tag once more; if it is now higher and
the image pointers were moved, it emits a warning naming the version. It does not move them back,
because it cannot know that the other version's image exists or can be trusted. The fix is to
re-dispatch the higher version, whose own late checks repoint them. If that higher tag was created
outside this workflow and has no image, retag by hand, after checking the digest you point at:

```bash
IMAGE=ghcr.io/leinardi/bitgauge
DIGEST=sha256:...   # the digest of the image that should be latest
gh attestation verify "oci://$IMAGE@$DIGEST" --repo leinardi/bitgauge \
  --signer-workflow leinardi/bitgauge/.github/workflows/release.yaml --source-ref refs/heads/main
docker buildx imagetools create -t "$IMAGE:latest" -t "$IMAGE:<major>" "$IMAGE@$DIGEST"
```

## Scheduled Scan

A release is scanned once, when it is built, but vulnerabilities keep being published.
`scheduled-scan.yaml` runs `make audit-deps` over `main`'s dependencies and, once releases exist,
resolves `:latest` to its index digest once and scans each platform image by its own digest with
the release's Trivy version, command and `.trivyignore`. Any finding fails the run. The published
image is immutable, so the fix is a new release: an explicit version when only a base image changed
(see [Versioning](#versioning)). It is **dispatch-only** while the repository is private; the
weekly schedule is restored by the going-public checklist.

## What the Workflows Trust

**Every action is pinned to a full commit SHA**, with the version in a trailing comment, in every
workflow, reusable and warm-up workflows included. A tag is a mutable pointer, and an action that
moves, or whose repository is compromised, would execute inside the release job, which holds
`contents: write`, `packages: write` and an OIDC identity. A SHA cannot be moved. Dependabot's
`github-actions` ecosystem updates the pins and rewrites the comment.

**Every image the release job runs is pinned by digest**: the job-local registry
(`REGISTRY_IMAGE`) and skopeo (`SKOPEO_IMAGE`) in the workflow's `env`, and the stage images and the
`# syntax=docker/dockerfile:…` BuildKit frontend in the Dockerfile. Dependabot's `docker` ecosystem
updates only the stage images, so the others are bumped by hand: resolve the new index digest with
`docker buildx imagetools inspect <image>:<tag>` and replace the tag and the digest together. `svu`
(`SVU_VERSION`) and Trivy (`TRIVY_VERSION`, in both `release.yaml` and `scheduled-scan.yaml`) are
pinned as versions and bumped by hand for the same reason; `test/toolchain/pins_test.go` holds them
to one value. Pinning Trivy does not pin what it knows: its vulnerability database is fetched at run
time, which is the point of scanning at release time.

**Workflow tokens are read-only by default.** Every workflow sets `permissions: contents: read` at
the top, and only the jobs that need more say so; the release job is the only one with write access
to the repository and the registry.

A SHA pin fixes only the top-level ref, so the actions and reusable workflows the owner maintains
(`leinardi/gha-pre-commit-reviewdog-actions`, `leinardi/gh-reusable-workflows`) pin what they run
too. The warm-up workflows matter more than they look. They declare `permissions: contents: read`,
but every step in a job also gets the Actions cache token, which can write any cache key, and the
warm-ups run on `main`, so they write into the `main` cache scope that the release job restores. A
moved tag inside a warm-up could therefore poison what the release builds, attests and signs. Keep
the nested pins current in those repositories, and bump the pins here when they release.

## Dependabot

Monthly update pull requests for five ecosystems:

| Ecosystem | Scope | Commit prefix |
| --- | --- | --- |
| `gomod` | Go modules | `fix(deps)`, so a dependency fix alone is enough for a patch release |
| `npm` (`web/`) | runtime dependencies `fix(deps)`, devDependencies `chore(deps)` | as listed |
| `docker` | stage image digests in the Dockerfile | `chore(deps)`; a security fix ships with an explicit version ([Versioning](#versioning)) |
| `github-actions` | actions pinned by commit SHA | `chore(deps)` |
| `pre-commit` | hook revisions in `.pre-commit-config.yaml` | `chore(deps)` |

Every update passes the same CI as any other pull request. Docker digest updates pull from
`dhi.io`, so Dependabot needs its own copy of the `dhi.io` token (see the setup below).

## Required Checks and Fork Pull Requests

The rulesets are managed as code in
[`leinardi/gh-leinardi-iac`](https://github.com/leinardi/gh-leinardi-iac), in the `repo_bitgauge`
module of `stacks/github-repos/repos.tf`, never by hand or with `gh api`: the ruleset on `main`
(pull requests only, no force push, no deletion) and the immutable `v*` tag ruleset. A change to
either is a pull request there.

The one required check is `ci-result`, set there as
`default_branch_required_checks = ["ci-result"]`. It needs every other job of `ci.yaml`
(`pre-commit-all`, `conventional-commits`, `repo-gates`, `release-scripts`, `go-test` and `audit`,
and the image, web, E2E and harness jobs once their gates activate) and fails unless each one
succeeded, so a new job becomes required by joining `ci-result`'s `needs`, not the ruleset. GitHub
counts a skipped required job as passing, which is why the jobs themselves are not listed. The
reviewdog annotation jobs are not needed by `ci-result`; they duplicate `pre-commit-all` as inline
comments.

Once the ruleset is applied, open one pull request and confirm the required check reports under
exactly the name `ci-result`. A required check that never reports blocks every merge.

Jobs that pull `dhi.io` images (the image build and its tests, the accuracy harness, release and
the scan's image job) need a **trusted run**: a push to `main`, a schedule or dispatch, a pull
request from a branch of this repository, or Dependabot. A pull request from a fork gets no
secrets, so those jobs are skipped with a notice, and `ci-result` fails on a fork pull request
whose image jobs were skipped. The image jobs have no path filter, so once they exist this applies
to every fork pull request, documentation-only ones included. `pull_request_target` is never used.

The only merge path for a fork pull request is then a **replacement pull request**: a maintainer
pushes the fork's commits unchanged (authorship preserved) to a branch of this repository, opens a
pull request that references the original, merges it once it is green, and closes the fork pull
request with a link. This path is **unverified** until it has been tested with a real fork from a
second account.

## One-Time Setup

Do these before the first dispatch, dry runs included. **The first release waits until the
repository is public**, because several pieces are limited on a private repository:

- Environments, environment secrets, deployment branch rules and rulesets need GitHub Pro, Team or
  Enterprise on a private repository. Without them `release.yaml` has no `dhi.io` credentials and
  the tag and branch rules are not enforced.
- Artifact attestations on a private repository need GitHub Enterprise Cloud. Without them the
  image attestation of fresh step 8, the binary attestations and the `gh attestation verify` check
  behind "Recovery, reuse" all fail.

This is one reason the process is [provisional](#release) and is revisited before going public.

1. **The `release` environment**, restricted to `main` with a deployment branch rule, as a
   server-side second line of defence behind the `guard` job. Add required reviewers too if a
   release should wait for a human. A run that references a missing environment creates it with no
   protection rules.
2. **The `dhi.io` credentials.** The build stages pull `dhi.io/golang` and `dhi.io/node`, the
   runtime stage `dhi.io/static`. Use a pull-only token:
   - the `DHI_USERNAME` Actions variable and the `DHI_TOKEN` Actions secret, for CI's trusted image
     jobs;
   - the same pair in the `release` environment, which `release.yaml` reads;
   - the same pair as **Dependabot** secrets named `DHI_USERNAME` and `DHI_TOKEN`, because
     Dependabot-triggered runs and the `dhi` registry in `.github/dependabot.yml` see only
     Dependabot secrets, not Actions variables.

   ```bash
   gh variable set DHI_USERNAME --body '<username>'
   gh secret set DHI_TOKEN
   gh variable set DHI_USERNAME --env release --body '<username>'
   gh secret set DHI_TOKEN --env release
   gh secret set DHI_USERNAME -a dependabot --body '<username>'
   gh secret set DHI_TOKEN -a dependabot
   ```

3. **Workflow permissions.** Every workflow is `contents: read` at the top. The `release` job adds
   `contents: write`, `packages: write`, `id-token: write` (cosign keyless and attestations) and
   `attestations: write`.
4. **Immutable tags.** A ruleset on `v*` tags with no update, no deletion and no bypass, managed in
   `gh-leinardi-iac` ([required checks](#required-checks-and-fork-pull-requests)).
5. **Branch protection** on `main`: pull requests only, and the required `ci-result` check, managed
   in `gh-leinardi-iac` ([required checks](#required-checks-and-fork-pull-requests)).
6. **Dependabot** enabled with the configuration above, and **private vulnerability reporting**
   enabled for [SECURITY.md](../SECURITY.md).
7. **GHCR package visibility (after the first release).** The first release creates
   `ghcr.io/leinardi/bitgauge`, already linked to the repository because a repository workflow
   pushed it. New packages are private, so set its visibility to public; until then nobody else can
   pull the image.
