# Release

How a BitGauge release is versioned, built and published, how the weekly rebuild keeps images
current, what to do when a release fails halfway, and what has to be set up by hand for all of it
to hold. The workflows are planned, not written yet; their shape is specified in
[features/technical-stack/build-packaging.md](features/technical-stack/build-packaging.md).

**There has been no release yet.** Before the first one, do the [one-time setup](#one-time-setup);
its first step can only be finished after the first release.

## What a Release Produces

- Two static binaries, `bitgauge-linux-amd64` and `bitgauge-linux-arm64`, built with
  `CGO_ENABLED=0` and `-trimpath`, with the version, commit and commit date compiled in and the SPA
  embedded. A `SHA256SUMS` file covers both. All three files are attached to the GitHub release.
- One multi-arch (`linux/amd64`, `linux/arm64`) image, `ghcr.io/leinardi/bitgauge`, with an SPDX
  SBOM and a `mode=max` SLSA provenance attestation for every platform image.
- A keyless [cosign](https://docs.sigstore.dev/) signature on the image digest, made with the
  release workflow's own GitHub OIDC identity; no signing key exists anywhere.
- The image tags of [Tags](#tags) and the GitHub "Latest" release marker when the version is the
  highest released one.
- Release notes generated by GitHub from the merged pull requests.

[SECURITY.md](../SECURITY.md) shows how to verify an image or a binary.

## How to Release

1. Make sure `main` is green and that the manual floor and ceiling tiers of the accuracy harness,
   and the real Safari and iOS checks, have passed for this commit and are recorded in
   [engineering/](engineering/README.md). A release is blocked until they have
   ([features/technical-stack/testing.md §6](features/technical-stack/testing.md#6-ci-placement)).
2. On an up-to-date `main`, compute the version with `svu next` (see [Versioning](#versioning)), or
   choose it explicitly.
3. Create the annotated tag `vX.Y.Z` on that commit and push it. The tag triggers `release.yaml`,
   which builds, pushes, signs and attests, then creates the GitHub release.

One release runs at a time: `release.yaml` and `rebuild.yaml` share one concurrency group without
cancellation, so a second tag, or a weekly rebuild, queues behind a running release instead of
racing it for the moving tags.

## Versioning

Semantic versioning, derived from
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) by [`svu`](https://github.com/caarlos0/svu):

- `feat` is a minor.
- `fix` is a patch.
- `!` before the colon, or a `BREAKING CHANGE:` footer, is a major. Before `1.0.0`, `svu` turns a
  breaking change into `1.0.0` straight away; while BitGauge is on `0.x`, tag a breaking change
  with an explicit version if it should stay on `0.x`.

Everything else (`build`, `chore`, `ci`, `docs`, `perf`, `refactor`, `revert`, `style`, `test`)
bumps nothing. A change users should receive is committed as `fix` or `feat`. When no commit since
the last release is a `feat`, a `fix` or a breaking change, `svu next` returns the current version
and there is nothing to release.

Only strict `vMAJOR.MINOR.PATCH` git tags are releases (no pre-release or build suffixes), and a
new version must be higher than every version already released. **A published tag is never moved,
deleted or reused.** A tag counts as published once its run has pushed any image or created the
GitHub release; the only tag that may be deleted and recreated is one whose run failed before
either happened ([Recovering a Failed Release](#recovering-a-failed-release)).

## Tags

| Image tag | Points to | Moves on |
| --- | --- | --- |
| `ghcr.io/leinardi/bitgauge:X.Y.Z` | that release | the weekly rebuild of the latest release (new digest, same version) |
| `ghcr.io/leinardi/bitgauge:X` | the latest release of major `X` | every release of major `X`, and its weekly rebuild |
| `ghcr.io/leinardi/bitgauge:latest` | the latest release | every release, and its weekly rebuild |

The git tag carries a `v` prefix (`vX.Y.Z`); image tags do not. Only GHCR is published.

## Weekly Rebuild

`rebuild.yaml` runs weekly and on manual dispatch. It exists so base-image security fixes reach
users without a code change.

**What it does:**

- Rebuilds the **latest release only**: the source code at that release's tag, with the three stage
  images (Node, Go and `dhi.io/static`) at the digests currently pinned on `main`, which Dependabot
  keeps current. The Dockerfile takes the stage images as build arguments, and the workflow reads
  their values from `main`'s Dockerfile.
- Pushes the result under the same tags (`X.Y.Z`, `X`, `latest`): **same version, new digest**.
  It runs in the same concurrency group as `release.yaml`, and just before pushing it re-checks that
  its version is still the highest release. If a newer release appeared meanwhile, it pushes only
  `X.Y.Z` and leaves `X` and `latest` alone, so a rebuild can never roll them back to an older
  version.
- Generates a new SBOM and provenance and signs the new digest, with the identity of
  `rebuild.yaml`.
- Ends without pushing when none of the three stage digests changed since the last build.

**What it does not do:**

- It never changes BitGauge's own code or dependencies: those change only through a release.
- It does not rebuild the release binaries. They are static and contain no base image; a Go
  standard-library fix reaches them only through a new release.
- It does not rebuild older versions. Pinning `X.Y.Z` receives base-image fixes only while it is
  the latest release; upgrading is the way to keep receiving them. Pinning by digest gives a fixed
  image that never changes.

## Dependabot

Weekly update pull requests for four ecosystems:

| Ecosystem | Scope | Commit prefix |
| --- | --- | --- |
| `gomod` | Go modules | `fix(deps)`, so a dependency fix alone is enough for a patch release |
| `npm` (`web/`) | runtime dependencies `fix(deps)`, devDependencies `chore(deps)` | as listed |
| `docker` | stage image digests in the Dockerfile | `chore(deps)`; the weekly rebuild ships them, a release is not needed |
| `github-actions` | actions pinned by commit SHA | `chore(deps)` |

Every update passes the same CI as any other pull request.

## One-Time Setup

1. **GHCR package visibility (after the first release).** The first release creates
   `ghcr.io/leinardi/bitgauge`, already linked to the repository because a repository workflow
   pushed it. New packages are private, so set its visibility to public; until then nobody else can
   pull the image.
2. **Workflow permissions.** `release.yaml` and `rebuild.yaml` need `contents: write` (release
   only), `packages: write`, `id-token: write` (cosign keyless and attestations) and
   `attestations: write`; every other workflow stays read-only.
3. **Tag protection.** A ruleset on `v*` tags so only maintainers can create, update or delete
   them. A maintainer deletes a tag only in the first recovery case below, before anything was
   published.
4. **Branch protection** on `main`: pull requests only, CI required.
5. **Dependabot** enabled with the configuration above, and **private vulnerability reporting**
   enabled for [SECURITY.md](../SECURITY.md).

## Recovering a Failed Release

- **Failed before anything was pushed** (a build or test failure, no image pushed and no GitHub
  release created): nothing is published, so the tag is not yet published either. Fix the cause on
  `main`, have a maintainer delete the tag, and tag the fixed commit with the same version. This is
  the only case in which a tag is deleted.
- **Image pushed, later step failed** (signing, attestation or the GitHub release): re-run the
  failed jobs of the same workflow run. They operate on the digest already pushed, so the version
  keeps one image. Never rebuild into a published `X.Y.Z` from a new run.
- **Published release is broken:** do not move or delete it. Fix forward with `X.Y.(Z+1)`.
- **Weekly rebuild failed:** nothing changes for users; the tags still point at the previous
  digest. Re-run it after fixing the cause, or let the next week's run pick it up.
