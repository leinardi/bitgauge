# Release

How a BitGauge release is versioned, built and published, how the weekly rebuild keeps images
current, what to do when a release fails halfway, and what has to be set up by hand for all of it
to hold. The workflows are not written yet: `release.yaml` and `rebuild.yaml` land together once
the image and web build gates are active, and their shape is specified here and in
[features/technical-stack/build-packaging.md](features/technical-stack/build-packaging.md#4-ci-workflows).

> [!IMPORTANT]
> **Provisional: the release process must be revised before the repository goes public.** It
> follows Runhold's model, chosen while the repository is private; the
> [going-public checklist](engineering/README.md) revisits it before the first public release.

**There has been no release yet.** Before the first dispatch, dry runs included, do the
[one-time setup](#one-time-setup).

## What a Release Produces

- Two static binaries, `bitgauge-linux-amd64` and `bitgauge-linux-arm64`, built with
  `CGO_ENABLED=0`, `-trimpath` and `-buildvcs=false`, with the version, commit and commit date
  compiled into `internal/buildinfo` and the SPA embedded. A `SHA256SUMS` file covers both. All
  three files are attached to the GitHub release, and each binary has a
  [build provenance attestation](https://docs.github.com/actions/security-guides/using-artifact-attestations)
  made by the release workflow.
- One multi-arch (`linux/amd64`, `linux/arm64`) image, `ghcr.io/leinardi/bitgauge`, with an SPDX
  SBOM and a `mode=max` SLSA provenance attestation for every platform image, a build provenance
  attestation, and a keyless [cosign](https://docs.sigstore.dev/) signature on the image digest,
  made with the release workflow's own GitHub OIDC identity; no signing key exists anywhere. Both
  platform images were scanned with [Trivy](https://trivy.dev/) before the version was tagged and
  had no `HIGH` or `CRITICAL` vulnerability outside the `.trivyignore` at the repository root.
- The image tags of [Tags](#tags) and the GitHub "Latest" release marker when the version is the
  highest released one.
- Release notes generated by GitHub from the merged pull requests.

[SECURITY.md](../SECURITY.md#verifying-a-release) shows how to verify an image or a binary.

## How to Release

1. Make sure `main` is green and that the manual floor and ceiling tiers of the accuracy harness,
   and the real Safari and iOS checks, have passed for this commit and are recorded in
   [engineering/](engineering/README.md). A release is blocked until they have
   ([features/technical-stack/testing.md §6](features/technical-stack/testing.md#6-ci-placement)).
2. Run the **Release** workflow (`release.yaml`) from the Actions tab, or
   `gh workflow run release.yaml`, on `main`. It is `workflow_dispatch` only and takes two inputs:
   - `version`: optional, `X.Y.Z` or `vX.Y.Z`. Left empty, the version is derived from the
     commits since the last release (see [Versioning](#versioning)). The first release needs it,
     since there is no tag to derive from. Give it explicitly to force a version, or to recover a
     failed run with a fresh dispatch.
   - `dry_run`: boolean, default `false`. See [Dry Runs](#dry-runs).

Nobody creates or pushes a tag by hand: the workflow builds, scans and verifies everything first,
and pushes the tag itself only then (see
[Why the Build Happens Before the Tag](#why-the-build-happens-before-the-tag)).

**One publish runs at a time.** `release.yaml` and `rebuild.yaml` share the `publish` concurrency
group with `cancel-in-progress: false`, so a second dispatch, or a weekly rebuild, queues behind a
running release instead of racing it for the moving tags.

## Versioning

Semantic versioning, derived from
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) by [`svu`](https://github.com/caarlos0/svu):

- `feat` is a minor.
- `fix` is a patch.
- `!` before the colon, or a `BREAKING CHANGE:` footer, is a major. Before `1.0.0`, `svu` turns a
  breaking change into `1.0.0` straight away; while BitGauge is on `0.x`, release a breaking change
  with an explicit version if it should stay on `0.x`.

Everything else (`build`, `chore`, `ci`, `docs`, `perf`, `refactor`, `revert`, `style`, `test`)
bumps nothing. A change users should receive is committed as `fix` or `feat`. When no commit since
the last release is a `feat`, a `fix` or a breaking change, a run with no version **fails** and
asks for an explicit version; there is nothing to release. The one exception is a recovery: when
`svu next` answers a strict tag that already sits on `HEAD`, the run treats it as a recovery of
that version, not as "nothing to bump", so re-running a failed run that derived its version works.

Only strict `vMAJOR.MINOR.PATCH` git tags are releases: `v`, then three dot-separated numbers, each
`0` or a number with no leading zero, and nothing after them. An explicit version must match too,
so pre-release and build suffixes are refused. Every lookup filters the full tag list through that
regex, never a glob, so pointer or malformed tags never become the current version. `svu` is given
the exact tag to count from: the highest strict tag reachable from `HEAD`, passed literally as
`--tag.pattern`.

A new version must be higher than every version already released. **A pushed tag is never moved,
deleted or reused**: an immutable-tags ruleset forbids it, and the workflow never needs it, because
the tag is pushed only after everything that can fail without a tag has succeeded. The only
version a run may reuse is the one it is recovering, which is exactly that tag already sitting on
`HEAD`.

## Why the Build Happens Before the Tag

The `v*` tags are protected by an immutable-tags ruleset (no update, no deletion, no bypass), so a
"delete the tag on failure" cleanup cannot exist. Everything that can fail without a tag happens
before the tag exists, and everything after it can be finished by a re-run on the tagged commit.

Jobs: `guard` (fails, rather than skips, when the ref is not `main`; every other job waits on it),
`go-test` and `web` (the same reusable workflows `ci.yaml` calls), `audit` (`make audit-deps`), and
`release`, which runs in the `release` environment with `contents: write`, `packages: write`,
`id-token: write` and `attestations: write`. Its steps are written for a **fresh** release; steps
5 to 10 depend on the mode decided in step 3, and how the recovery modes differ is under
[Recovering a Failed Release](#recovering-a-failed-release):

1. **Resolve the version** with `svu next --tag.pattern <exact highest tag>`, or take the explicit
   one, and run the regex and monotonic checks of [Versioning](#versioning).
2. **Create the tag locally only**, annotated with the exact Go and Node versions the binaries are
   built with, so a later recovery can rebuild with the same toolchains.
3. **Decide the mode**, fail-closed, from lookups made before anything is built or pushed: the git
   tag on the remote and the image's `:X.Y.Z` on GHCR. Only "not found" counts as absent; an
   authentication or network error stops the run.

   | Git tag | Image `:X.Y.Z` | Mode |
   | --- | --- | --- |
   | absent | absent | **Fresh** |
   | absent | present | **Stop before tagging**: the version is held by an image |
   | on this commit | present, attested by this workflow for this commit | **Recovery, reuse** |
   | on this commit | present, not attested by this workflow | **Stop: needs a human** |
   | on this commit | absent | **Recovery, publish** |
   | anywhere else | any | **Stop**: the version belongs to another commit |

4. **Build** the web app, then the two static binaries and `SHA256SUMS`.
5. **Build the image once**, for both platforms, with one `docker/build-push-action` run: SBOM,
   `mode=max` provenance, gzip layers, pushed by digest to a registry inside the job
   (`registry:3.1.2`, pinned by digest), after logging in to `dhi.io` for the build stages. There is
   no other image build: what is scanned is what is published.
6. **Scan** both platform images, each by its own digest, with Trivy:
   `--scanners vuln --severity HIGH,CRITICAL --exit-code 1`. A finding fails the run with no tag
   anywhere. A vulnerability with no fix yet still blocks unless it is accepted in `.trivyignore`
   with a reason and an expiry date.
7. **Gate the tag again**: the highest released version is read again from the remote, and the
   image `:X.Y.Z` is checked absent with the same fail-closed lookup.
8. **Push the tag**: the point of no return.
9. **Copy to GHCR by digest** with skopeo (pinned by digest), untagged, preserving the index
   digest, which must equal the scanned one.
10. **Attest and sign** the digest (`cosign sign --yes`), then tag it `X.Y.Z`, after checking once
    more that the tag is absent.
11. **Attest the binaries** through `.github/scripts/binary-attestation-status.sh`, which reuses an
    attestation an earlier run made and fails closed on any answer it cannot classify.
12. **Create the GitHub release as a draft** and reconcile its assets: a present asset is compared
    by SHA-256 with this run's build, a missing one is uploaded, an unexpected one fails the run.
13. **Move `X` and `latest`**, and publish the release as "Latest", only if the version is still
    the highest when each pointer is moved; then publish the draft.

An existing tag is reused only after
`gh attestation verify --signer-workflow leinardi/bitgauge/.github/workflows/release.yaml` binds
the image to this repository, this workflow and this commit.

## Dry Runs

`dry_run: true` rehearses a fresh release: it resolves the version, decides the mode, builds the
binaries and the image, scans both platform images and copies the index to a second job-local
registry instead of GHCR. It pushes no tag and publishes no image and no release. The job summary
shows the version, the mode a real run would take, the toolchain versions and the digests. A dry
run with no version is also the quickest way to see what version the commits would produce.

## Tags

| Image tag | Points to | Moves on |
| --- | --- | --- |
| `ghcr.io/leinardi/bitgauge:X.Y.Z` | that release | the weekly rebuild of the latest release (new digest, same version) |
| `ghcr.io/leinardi/bitgauge:X` | the latest release of major `X` | every release of major `X`, and its weekly rebuild |
| `ghcr.io/leinardi/bitgauge:latest` | the latest release | every release, and its weekly rebuild |

The git tag carries a `v` prefix (`vX.Y.Z`); image tags do not. Only GHCR is published. Image tags
move; the git tag never does.

## Weekly Rebuild

`rebuild.yaml` runs weekly and on manual dispatch, in the same `publish` concurrency group. It
exists so base-image security fixes reach users without a code change.

**What it does:**

- Rebuilds the **latest release only**: the source code at that release's tag, with the three stage
  images (`web`, `build` and `runtime`) at the digests currently pinned on `main`, which Dependabot
  keeps current. It reads `main`'s `deployments/docker/Dockerfile` and rewrites the tag's `FROM`
  lines **by stage name**. The stage images are literal `FROM` lines, not build arguments, because
  Dependabot updates only literal `FROM` lines.
- **Checks the toolchain line first.** A rebuild may refresh digests and patch versions only: for
  `build` and `web`, main's `FROM` must keep the image repository, the Go `major.minor` or the
  Node major, and the tag shape apart from a patch version; for `runtime`, the repository and
  variant must match and the date tag may move. Anything else fails with a notice such as "main
  moved build from Go 1.26 to 1.27; vX.Y.Z keeps 1.26, so cut a release to ship the new line, or
  pin the old line".
- Ends without pushing when main's three digests equal the base-image materials recorded in the
  current `:X.Y.Z` image's provenance.
- Otherwise builds to a job-local registry, scans with Trivy as a release does, re-checks that its
  version is still the highest release, pushes by digest, generates a new SBOM and provenance and
  signs the new digest with the identity of `rebuild.yaml`, and retags `X.Y.Z`. It moves `X` and
  `latest` only if the version is still the highest, so a rebuild can never roll them back.

**What it does not do:**

- It never changes BitGauge's own code or dependencies: those change only through a release.
- It does not rebuild the release binaries. They are static and contain no base image; a Go
  standard-library fix reaches them only through a new release.
- It does not rebuild older versions. Pinning `X.Y.Z` receives base-image fixes only while it is
  the latest release; upgrading is the way to keep receiving them. Pinning by digest gives a fixed
  image that never changes.

## Scheduled Scan

A release is scanned once, when it is built, but vulnerabilities keep being published.
`scheduled-scan.yaml` runs `make audit-deps` over `main`'s dependencies and, once releases exist,
scans each platform image of `:latest` with the release's Trivy version and command. Any finding
fails the run. It is **dispatch-only** while the repository is private; the weekly schedule is
restored by the going-public checklist.

## Dependabot

Weekly update pull requests for five ecosystems:

| Ecosystem | Scope | Commit prefix |
| --- | --- | --- |
| `gomod` | Go modules | `fix(deps)`, so a dependency fix alone is enough for a patch release |
| `npm` (`web/`) | runtime dependencies `fix(deps)`, devDependencies `chore(deps)` | as listed |
| `docker` | stage image digests in the Dockerfile | `chore(deps)`; the weekly rebuild ships them, a release is not needed |
| `github-actions` | actions pinned by commit SHA | `chore(deps)` |
| `pre-commit` | hook revisions in `.pre-commit-config.yaml` | `chore(deps)` |

Every update passes the same CI as any other pull request, except that the `signoff` check
exempts commits authored by `dependabot[bot]`, which carry no `Signed-off-by`. Docker digest
updates pull from
`dhi.io`, so Dependabot needs its own copy of the `dhi.io` token (see the setup below).

## Required Checks and Fork Pull Requests

The branch ruleset on `main` requires these checks: `pre-commit-all`, `repo-gates`, `go-test`,
`audit`, `conventional-commits`, `signoff` and `ci-result`. The reviewdog annotation jobs are not
required; they duplicate `pre-commit-all` as inline comments.

Jobs that pull `dhi.io` images (the image build and its tests, the accuracy harness, release,
rebuild and the scan's image job) need a **trusted run**: a push to `main`, a schedule or dispatch,
a pull request from a branch of this repository, or Dependabot. A pull request from a fork gets no
secrets, so those jobs are skipped with a notice, and `ci-result` fails on a fork pull request
whose image jobs were skipped. The image jobs have no path filter, so once they exist this applies
to every fork pull request, documentation-only ones included. `pull_request_target` is never used.

The only merge path for a fork pull request is then a **replacement pull request**: a maintainer
pushes the fork's commits unchanged (authorship and `Signed-off-by` preserved) to a branch of this
repository, opens a pull request that references the original, merges it once it is green, and
closes the fork pull request with a link. This path is **unverified** until it has been tested with
a real fork from a second account.

## One-Time Setup

Do these before the first dispatch, dry runs included. **The first release waits until the
repository is public**, because several pieces are limited on a private repository:

- Environments, environment secrets, deployment branch rules and rulesets need GitHub Pro, Team or
  Enterprise on a private repository. Without them `release.yaml` has no `dhi.io` credentials and
  the tag and branch rules are not enforced.
- Artifact attestations on a private repository need GitHub Enterprise Cloud. Without them the
  image attestation of step 10, the binary attestations of step 11 and the `gh attestation verify`
  check behind "Recovery, reuse" all fail.

This is one reason the process is [provisional](#release) and is revisited before going public.

1. **The `release` environment**, restricted to `main` with a deployment branch rule, as a
   server-side second line of defence behind the `guard` job. A run that references a missing
   environment creates it with no protection rules.
2. **The `dhi.io` credentials.** The build stages pull `dhi.io/golang` and `dhi.io/node`, the
   runtime stage `dhi.io/static`. Use a pull-only token:
   - the `DHI_USERNAME` Actions variable and the `DHI_TOKEN` Actions secret, for CI's trusted image
     jobs;
   - the same pair in the `release` environment, which `release.yaml` and `rebuild.yaml` read;
   - the same token as a **Dependabot** secret named `DHI_TOKEN`, because Dependabot-triggered runs
     and the `dhi` registry in `.github/dependabot.yml` see only Dependabot secrets.

   ```bash
   gh variable set DHI_USERNAME --body '<username>'
   gh secret set DHI_TOKEN
   gh variable set DHI_USERNAME --env release --body '<username>'
   gh secret set DHI_TOKEN --env release
   gh secret set DHI_TOKEN -a dependabot
   ```

3. **Workflow permissions.** Every workflow is `contents: read` at the top. The `release` job adds
   `contents: write`, `packages: write`, `id-token: write` (cosign keyless and attestations) and
   `attestations: write`; `rebuild.yaml` the same without `contents: write`.
4. **Immutable tags.** A ruleset on `v*` tags with no update, no deletion and no bypass.
5. **Branch protection** on `main`: pull requests only, and the
   [required checks](#required-checks-and-fork-pull-requests).
6. **Dependabot** enabled with the configuration above, and **private vulnerability reporting**
   enabled for [SECURITY.md](../SECURITY.md).
7. **GHCR package visibility (after the first release).** The first release creates
   `ghcr.io/leinardi/bitgauge`, already linked to the repository because a repository workflow
   pushed it. New packages are private, so set its visibility to public; until then nobody else can
   pull the image.

## Recovering a Failed Release

Nothing needs deleting: a failed run either pushed no tag, or pushed one that a re-run can finish.

- **Failed before the tag was pushed** (a test, build, scan or gate failure): nothing is
  published. Fix the cause on `main` and dispatch again.
- **Failed after the tag was pushed** (copy, signing, attestation or the GitHub release): use
  **"Re-run failed jobs"** on the same run, which keeps its commit and inputs, or dispatch again
  with the same version given explicitly while `main` still points at the tagged commit. The mode
  decision picks **recovery, reuse** (the published image is verified by its attestation and
  signature and reused by digest; the binaries are rebuilt with the toolchains recorded in the tag
  and checked against the release assets) or **recovery, publish** (the image is absent, so it is
  rebuilt, scanned and published). If the scan now fails because a vulnerability was published
  since, the version is abandoned and the fix ships as a higher version.
- **Published release is broken:** do not move or delete anything. Fix forward with
  `X.Y.(Z+1)`.
- **A stop row of the mode table:** something outside this workflow holds the version. Nothing is
  overwritten; release a higher version.
- **Weekly rebuild failed:** nothing changes for users; the tags still point at the previous
  digest. Re-run it after fixing the cause, or let the next week's run pick it up. A toolchain-line
  failure is fixed by cutting a release, not by re-running.
